### 1.2 Jobs to be done — are the user's main intentions handled?

**Job A — "Log what I ate, fast, with as little thinking as possible."**

What I measured on the built app (stub AI, 390 × 844):

| Path                             | Taps to save                              | Wait                                     | What gets in the way                                                                                                                                                          |
| -------------------------------- | ----------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Planned meal, option, as written | 3 (Log this meal → option → Save)         | none                                     | The review is a 1,438 px scroll of three full edit cards ("Estimated" badge, quantity, unit, Unknown checkbox, pencil, trash) before Save. The user came to say "I ate this". |
| Text, any language               | 3 + typing (Analyze → notice once → Save) | 2–4 s live (16 s on the first cold call) | Good. If the model asks a portion question, answering it changes nothing (defect 1).                                                                                          |
| Photo                            | 4 + camera                                | 3–4 s live                               | The photo is not shown on the review; portion questions dead-end; the item named by the model cannot be corrected and re-estimated without losing the correction (defect 2).  |
| "I ate something else for lunch" | blocked                                   | —                                        | Must pick one of four lunch options that were not eaten, or file it as "Other" and lose the honest "Different food" row (defect 3).                                           |
| Recent meal                      | 2                                         | none                                     | Works; the chip is titled by the first item's Persian name only, so three similar breakfasts look identical.                                                                  |
| Manual                           | 2 + form                                  | none                                     | The typed description is shown but not turned into an item; the user re-types the name. No estimate ever, unless label values are typed.                                      |

Where the cognitive load actually sits:

1. **One composer for six intents.** Opening from "Log this meal" on breakfast, the first thing on screen is an empty "What did you eat?" box and "Add photo"; the three breakfast options are cut off at the bottom of the viewport (`19-composer-planned.png`). The spec's own wording is "the user picks the option first". The decision the user came to make should be the first thing they see, with free text as the escape hatch, not the other way round.
2. **The review treats every item as something to edit.** For a planned meal eaten as prescribed, the right review is one line per item and one Save; editing is the exception. Today the exception is the default, and the affordances (badges, checkboxes, unit dropdowns) all compete for attention.
3. **Uncertainty resolution is a dead end.** The spec's central idea for photos — "group essential questions on the review screen instead of starting an endless chat" — is built as UI but not as behaviour. An answer is a string in the draft; nothing reads it. The user's only options are to type a quantity (which still yields no nutrition because there is no base estimate to scale, `scale.ts` returns `UNCHANGED` for null nutrition) or to press Re-estimate, which asks the same question again.
4. **Slot linking is implicit.** After analysis the review shows "Meal slot · Not chosen yet · Change". The live model suggested a slot in 5/5 probes, so most users will not hit this, but when the suggestion is null the meal silently becomes "Other". The spec asks for one suggested link and an explicit choice.

**Job B — "See how I'm doing against my plan."**

This job is served well, and honestly. Today answers "what is recorded, how does it compare, what next" in that order; the score is always paired with coverage ("Based on 2 of 5 prescribed meals"), the band wording is neutral, "Why this score" lists each component, and unknowns stay unknown. The rubric is deterministic and versioned. A user can explain the number in their own words — the spec's usability test — after one expansion.

Where it falls short of "at a glance":

- **First paint is the paragraph, not the state.** On a phone, the reflection card occupies the top ~370 px; the score and the next action start at the fold (`18-today-viewport.png`). The reflection is the interpretation; the plan block is the answer. On a first visit with nothing recorded, the score card still renders a heading, "Not enough information yet" and a "Why this score" disclosure — empty chrome above the one useful action.
- **Status is words.** Five rows of "Not recorded / Mark skipped" look identical to each other and to a recorded row until you read them. There is no check / dash / circle glyph, no count ("2 of 5 recorded") on the card, no progress bar in nutrition details. A user scanning for "am I on track" has nothing to scan.
- **Prescribed meal vs. its own range.** Logging breakfast option 1 exactly as written produced "Above this meal's range by 80 kcal" because the plan's AI-estimated baseline for the option (480 kcal) exceeds the plan's stated 300–400 range. With the stub the numbers are canned, but the same collision will happen with the live baseline whenever a dietitian's approximate range and the model's estimate disagree — and it will happen to the user who did everything right. The comparison should be suppressed (or labelled as a plan-internal inconsistency) when the meal is the prescribed option with portions as planned.
- **History in week one.** A new user sees six rows of "No meals recorded" for days before the account existed, plus "Your plan changed during these days" (it did not change; it was created — `planChangedBetween` keys off `confirmedAt`). The first impression of History is "you failed six days and changed your plan".

### 1.4 Product risks the owner should decide on

1. **The AI's questions must feed the estimate.** Either (a) send the answered questions and the user's item edits back with the re-estimate request so the model returns scaled values, or (b) map choice answers to quantities client-side using the unit table ("a can (330 ml)" → 330 ml). (a) is the only path that also fixes renamed items. Until then the photo flag should stay off, not because the vision model is weak (it was good in my probe) but because the review cannot finish what the model starts.
2. **Option requirement vs. replacement meals.** Decide the rule: an option is required only when the recorded items overlap an option (the "I ate this" path); a meal with no overlap saves under the slot as "Different food" with no option. The spec (§ 8 "replacement versus extra", J5) already implies this; the code applies the J2 rule to every case.
3. **Prescribed-option baseline vs. stated range.** Decide whether the per-meal energy line is shown at all when the meal is the prescribed option with portions as planned.
4. **Reflection guard is honesty-based.** `checkReflection` verifies that every `usedFactIds` entry exists; it cannot see prose. The stub's paragraph ("This reflection covers the meals you recorded yesterday…") passed on a day with no yesterday, claiming only `ctx:*` and `today:plan`. The live model was grounded in 3/3 probes, but there is no prompt line telling it "this is the user's first day; welcome them" — the first-day state is expressed only by the absence of yesterday facts. The fallback library has a proper FIRST_DAY paragraph; the AI path does not know the state exists.
5. **"Complete by default" facts reach the paragraph.** In the eval fixture "1 of 5 meals recorded, checked", the fact list includes "energy total was below the planned range by 950 kcal" and the live paragraph repeated it. The spec allows the day to be _treated_ as complete, but telling a user who logged one meal that they were 950 kcal short is the "unfinished-day reprimand" § 8 warns against. Consider withholding the energy fact when coverage is "complete by default".

### 1.5 Smaller UX findings (P3)

- Rule review shows only the source text ("ماهی دو بار در هفته"); it never shows what the app _understood_ (Fish · at least 2 per week). The review exists to confirm the interpretation.
- "Change" is the label for a slot that has not been chosen; when pressed, a second "Meal slot" heading and select appear under the first.
- Unchecking "I don't remember the time" prefills 12:00 (`MealComposer.tsx`); the spec says never invent noon. A prefilled editable field is defensible, but an untouched 12:00 will be saved as the consumed time.
- "Add photo" `<input>` has no `capture` hint, so on phones it opens the gallery picker rather than the camera by default. Fine for the pilot; worth a decision.
- The Recent meals chip after a planned meal is titled "تخم‌مرغ" with "Egg, Sangak bread, Cucumber and tomato" beneath — the title should be the slot or the option.
- Planned-meal chips in the composer do not indicate that the slot is already recorded, so a second breakfast is one tap away.
- Meal details keeps the Log meal FAB, which covers the Photos section on a 390 px screen; the top bar title is empty on that route.
- Unit labels do not pluralise: "2 egg", "2 slice of sangak", "1 slice of sangak instead of 2 slice of sangak".

## 2. Senior UI Designer & visual expert

### 2.1 What is done well

- **Token discipline.** One palette, one radius scale, one spacing scale, no hex in components (`globals.css`, decision 019). Light and dark are both coherent; dark mode is not an afterthought (`41-today-dark.png`, `42-composer-dark.png`).
- **Bidirectional text.** Persian names beside English labels render correctly in every component I looked at — rows, chips, selects, inputs with `dir="auto"`, the "You wrote:" echo. `NameLabel`/`InlineName` with `<bdi>` is the right primitive and it is used consistently. This is the hardest visual problem in the product and it is solved.
- **Touch targets and hierarchy.** 44 px rows and buttons throughout, one primary per form, sentence case, calm copy. The onboarding screens are exemplary: one question, one field, one button (`06-onboarding-timezone.png`).
- **Progressive disclosure is real.** One `Disclosure` pattern everywhere (Why this score, slot details, nutrition details, sources, More details). Nothing important is hidden behind it.
- **Forms.** Labels above fields, errors wired, keyboards right (`inputmode` via `type=date/time`), Persian digits accepted.

### 2.2 Where the visual experience is not yet "lovely"

**1. Monotony.** Every block on every page is the same white card with the same 1 px border, the same 16 px padding, the same 14 px grey text. Today, History, My plan and Settings are visually the same page with different words. Nothing signals "this is the number that matters" except one 30 px numeral. Compare the Today viewport (`18-today-viewport.png`): heading, card, heading, card, card.

**2. Status has no shape.** The product's whole promise is "how does today compare"; the answer is rendered as text in `text-muted-foreground`. Five "Not recorded / Mark skipped" pairs stacked look like a settings list (`18c-today-scrolled.png`). The spec forbids colour-only status, not status glyphs. A small leading glyph per row (filled check = matched, half circle = partly, empty circle = not recorded, dash = skipped, dot = different) plus a "2 of 5 recorded" count on the score card would make the state scannable without any colour semantics.

**3. Iconography is on the wrong surfaces.** Icons are used on utility controls (pencil, trash, plus, camera, chevrons, the three tab icons) and inside difference chips — good — but not where the eye scans: slot state, score band, nutrient rows, meal rows (a tiny camera glyph for a meal with a photo), the reflection card. The result is that the pages that carry the most information (Today, review) are the ones with the fewest visual anchors.

**4. Two emerald CTAs per viewport.** The design rule in decision 019 is one filled primary per viewport. Today shows "Log this meal" (filled) inside the highlighted row while the "Log meal" FAB (filled) floats over it (`18c-today-scrolled.png`, `21b-…png`). They also do nearly the same thing. Either the row's action becomes secondary, or the FAB hides while a highlighted row's action is in view.

**5. Review density.** On "Check your meal", each item is a card with title, two badges, a two-column quantity/unit form, an "Unknown" checkbox, a values line and two icon buttons (`20-review-planned.png`). For a planned meal this is 3 × 210 px of controls the user will not touch. A compact row (name · quantity · kcal · chevron) that expands to the editor would halve the height and the visual noise, and would make the badges meaningful when they do appear.

**6. Nutrition details are a table of words.** "Energy 1,310 kcal · Target: About 1,800 kcal · Estimated from your plan · Recorded so far" × 4 (`31-nutrition-details.png`). A thin bar per nutrient (recorded vs. range, neutral colour, no red) communicates the same in a tenth of the reading time and fits the spec's "no charts" intent.

**7. Page-title duplication.** History, My plan and Settings show the title in the top bar _and_ as an `h1` directly beneath it (`38-history.png`, `40-settings.png`). On desktop the shell adds a second header row (tabs above the logo bar), so three horizontal bands sit above the content (`54-today-desktop.png`).

**8. Destructive styling.** "Delete account" is a full-width filled red button with the same weight as the primary CTA (`40b-settings-full.png`). Convention is an outline or text-destructive button with a confirm step.

**9. Small things that read as unfinished.**

- "Why this score ▾" rendered on a card that says "Not enough information yet".
- Progress bar at 100 % on "Step 8 of 8" for seven consecutive screens.
- "Meal slot / Change" then a second "Meal slot" label and select on the same card when Change is tapped (`27-review-change-slot.png`).
- Slot subline "3 options · choose what you ate · 300–400 kcal" wraps to two lines on 390 px and mixes an instruction with data.
- The "Estimated" badge on every item of a planned meal (the values came from the plan baseline, not this analysis).
- Long forms in plan "Fix" (every item fully expanded, `44-plan-edit-fix.png`) — correct, but a wall.

## 3. QA

### 3.1 Environment and method

- Local Postgres (`dietyaar-db`, port 5433), the dev server on :3000, the stub DeepSeek server on :3999 (`e2e/stub-ai`). The repo's `.env` points every local run at the stub, so anything you click locally returns canned data.
- To exercise the **photo path** end to end I started a throwaway MinIO container (`dietyaar-qa-minio`, bucket `dietyaar-qa`) and restarted the dev server with `S3_*` pointing at it. Without this, `/api/uploads` answers `503 STORAGE_UNAVAILABLE` on every dev machine and in CI — see 3.6.
- For **model quality** I ran the production prompts/adapter/schemas against the live endpoint (`DEEPSEEK_API_BASE_URL=https://api.deepseek.com`) through a scratchpad script: 3 Persian text meals with the menu-plan context, 1 photo-only, 1 photo + text, and 3 reflection states. Cost: a few cents.
- Accounts created: `qa_review_1` (full onboarding, menu plan, 4 meals incl. one photo, one plan edit) and `qa_review_2` (onboarding not started; used for the cross-account check). Two e2e runs overlapped once (my mistake), which caused one flaky failure that passed on re-run.

### 3.6 Coverage gaps and test-infrastructure notes

- **No photo e2e at all** (`grep -i photo e2e/*.spec.ts` → nothing). CI has no `S3_*` variables, so a photo spec could not run there either; the local `.env` has none, so nobody can click through the photo path on a dev machine without setting up storage. Suggest a MinIO service in `docker-compose.yml` and CI, plus one spec: upload → analyze (stub) → answer → save → details shows the photo.
- **Journeys without e2e:** J5 (replaced meal), J6 (backdate), J8 (uncheck), plan _replace_ (J10 second half). J5 would have caught D3.
- **Stub vs. reality:** the stub returns "Unknown dish" for every photo and never suggests a slot for text, so the e2e suite never exercises the AI-suggested-slot or answered-question paths — which is where D1/D5 live. A second stub scenario ("SUGGEST" token → returns a slot + a question) would close that.
- `ai:eval` meal fixtures are all `reviewed: false`, so the 96 % recall figure in the runbook is unreviewed.

### 3.7 Security spot checks (all ✅)

Photo route: wrong `s` tag, missing tag and another account's session all answer 404. `/api/uploads` refuses when `PHOTO_LOGGING_ENABLED=false` and enforces same-origin. Cookies are httpOnly; session tokens hashed; password change signs out other devices (e2e). CSP and security headers present (e2e). No health data in logs observed.

## 4. Recommendations, in order

1. **Close the loop on questions and re-estimate (D1, D2).** Send the user's current items (names, chosen quantities, answers) with the re-estimate request and have the model return values for _those_ items; keep the user's names. This one change turns the photo path from "identifies well, cannot finish" into a working feature.
2. **Fix the option rule (D3).** Require an option only when the recorded items overlap an option; otherwise save under the slot as Different food. Add the J5 e2e.
3. **Intent-aware composer.** When opened from a slot row, show the option list first (text and photo below as "Something else?"). When opened from the FAB, keep today's layout. Show the photo thumbnail(s) at the top of the review.
4. **Compact review for planned and recent meals.** One line per item, kcal at the end, chevron to edit, Save in view without scrolling.
5. **Give Today a scannable state.** Row glyphs, "2 of 5 recorded" on the score card, thin bars in nutrition details, one emerald per viewport, hide the "Why this score" disclosure until something is scored, collapse the reflection by default after the first read of the day.
6. **Copy and first-week fixes (D6–D8, D16):** past-day caption, "plan changed" only after the second confirmation, parse local dates without `T00:00:00`, hide pre-signup days.
7. **Test infrastructure:** MinIO in compose + CI, a photo e2e, a stub scenario that suggests a slot and asks a question, and e2e for J5/J6/J8.
